# NebulaTech 星云科技应用发布手册

## 发布环境

应用发布分为 Development、Staging 和 Production 三个环境。代码必须按照 Development → Staging → Production 的顺序推进；禁止从本地分支直接跳过 Staging 发布到 Production。

## Development

### 开发环境发布

具有项目写权限的工程师可在任意时间自助发布 Development，不需要人工审批。开发环境发布失败不会触发生产事故流程，但必须由提交人自行恢复可用状态。

## Staging

### Staging 发布审批

发布到 Staging 前，必须通过单元测试和静态检查，并由发起人的直属 Team Lead 审批。Staging 发布不要求当周值班 SRE 审批。

### 验证时长

准备进入 Production 的版本必须在 Staging 连续运行至少 2 小时，并通过冒烟测试。两小时从最近一次 Staging 成功部署完成时开始计算；期间重新部署会重新计时。

## Production

### Production 发布审批

Production 发布必须由 Release Manager 和当周值班 SRE 双人审批。两名审批人必须确认 Staging 验证结果、监控面板链接、回滚版本号和变更单编号均已填写。

### 发布窗口

常规 Production 应用发布窗口为每周三 20:00 至 22:00。法定节假日前最后一个工作日禁止执行常规 Production 发布。P0 或 P1 事故修复可使用紧急发布流程，不受常规窗口限制。

### 灰度发布

Production 默认先向 10% 实例发布并观察 10 分钟。若 5xx 错误率没有比发布前基线增加超过 2 个百分点，且 P95 延迟没有增加超过 20%，才可继续全量。

## 回滚流程

### 自动与人工回滚条件

发布后任意连续 5 分钟内，5xx 错误率超过 5%，或 P95 延迟比发布前基线增加超过 30%，必须启动回滚。满足条件后应在 15 分钟内完成回滚到变更单中记录的上一稳定版本。

### 回滚责任

Release Manager 负责宣布回滚并更新变更单；当周值班 SRE 负责确认流量、实例和监控指标恢复。回滚完成后不得直接再次发布同一版本，必须先修复触发回滚的问题并重新通过 Staging 两小时验证。

## 发布记录

所有 Staging 和 Production 发布记录保留 180 天。记录至少包含版本、提交人、审批人、开始时间、结束时间和结果。

## 发布原则与执行边界

三个发布环境承担不同目的。Development 用于工程师快速验证代码是否能够运行；Staging 用于在接近生产的配置下验证候选版本；Production 才承载真实客户流量。因此同一个版本在三个环境中的“发布成功”含义不同，Development 成功不能替代 Staging 验证，Staging 成功也不能替代 Production 审批。

发布审批针对应用版本，不自动覆盖数据库 Schema 变更、生产数据修复或安全策略调整。若同一次发布同时包含这些变更，发起人必须分别满足对应制度中的审批要求，并在同一变更单中建立关联。这样做是为了让检索到“Production 审批”时仍能区分应用发布和数据库变更两个对象。

灰度观察期间，Release Manager 不得因为单个健康检查成功就跳过完整观察。若指标触发回滚条件，团队首先恢复上一稳定版本，再分析失败原因；不能为了验证猜测而让已知异常版本继续扩大流量。

发布记录应能够还原“谁发布、谁批准、发布了什么、结果如何”。因此任何口头确认都不能替代变更单中的正式审批记录。
